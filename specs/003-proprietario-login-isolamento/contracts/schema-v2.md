# Contrato de estrutura — migração V2 (PostgreSQL, profile `prod`)

**Feature**: [../spec.md](../spec.md) (FR-022…FR-025, US4) · **Decisões**: [../research.md](../research.md) (R8, R9)
**Base**: V1 (`specs/001-better-db-schema/contracts/imoveis-schema.md`), que continua valendo sem mudança.

Arquivo: `src/main/resources/db/migration/V2__cria_usuarios_e_dono_de_imoveis.sql`.
Pré-condição: `imoveis` vazia (não há dados de produção). Sem migração de dados.

## Tabela nova `usuarios`

| Coluna | Tipo | Nulo | Observação |
|---|---|---|---|
| `id` | `bigint GENERATED BY DEFAULT AS IDENTITY` | não | |
| `nome` | `varchar(100)` | não | |
| `email` | `varchar(254)` | não | sempre normalizado |
| `senha_hash` | `varchar(60)` | não | hash BCrypt; `varchar` e não `char` (R9) |

| Restrição | Definição | Garante |
|---|---|---|
| `pk_usuarios` | `PRIMARY KEY (id)` | |
| `ck_usuarios_nome_nao_vazio` | `CHECK (nome !~ '^\s*$')` | FR-002 |
| `ck_usuarios_email_normalizado` | `CHECK (email = lower(btrim(email)) AND email <> '')` | FR-003; unicidade sem caixa por construção |
| `uq_usuarios_email` | `UNIQUE (email)` | FR-004 |
| `ck_usuarios_senha_hash_bcrypt` | `CHECK (senha_hash ~ '^\$2[aby]\$\d{2}\$[./A-Za-z0-9]{53}$')` | FR-006, SC-004: nunca texto puro |

## Alterações em `imoveis`

| Coluna nova | Tipo | Nulo |
|---|---|---|
| `usuario_id` | `bigint` | não |
| `identificador` | `varchar(50)` | não |

| Restrição | Definição | Garante |
|---|---|---|
| `fk_imoveis_usuario` | `FOREIGN KEY (usuario_id) REFERENCES usuarios (id) ON DELETE RESTRICT` | FR-013, FR-024, RNF-08 |
| `ck_imoveis_identificador_nao_vazio` | `CHECK (identificador !~ '^\s*$')` | FR-015 |
| `ck_imoveis_identificador_sem_espacos_nas_pontas` | `CHECK (identificador = btrim(identificador))` | FR-015 (o domínio grava já sem espaços) |
| `uq_imoveis_usuario_identificador` | `CREATE UNIQUE INDEX ... ON imoveis (usuario_id, lower(identificador))` | FR-016, Clarifications Q5 |

O índice único também serve à FK (começa por `usuario_id`); não é preciso índice extra.
`varchar(n)` no PostgreSQL conta caracteres, não bytes — coerente com o domínio (code points).

## Garantias a provar (testes de integração contra PostgreSQL)

| # | Tentativa direta no banco | Esperado |
|---|---|---|
| G-U1 | `usuarios` com `nome` só espaços | recusada por `ck_usuarios_nome_nao_vazio` |
| G-U2 | `usuarios` com `email` em maiúsculas ou com espaço | recusada por `ck_usuarios_email_normalizado` |
| G-U3 | dois `usuarios` com o mesmo `email` | segundo recusado por `uq_usuarios_email` |
| G-U4 | `usuarios` com `senha_hash = 'segredo123'` | recusada por `ck_usuarios_senha_hash_bcrypt` |
| G-I1 | `imoveis` sem `usuario_id` | recusada (`NOT NULL`) |
| G-I2 | `imoveis` com `usuario_id` inexistente | recusada por `fk_imoveis_usuario` |
| G-I3 | `imoveis` com `identificador` vazio, só espaços ou com espaço nas pontas | recusada pelos `CHECK` |
| G-I4 | `imoveis` com `identificador` de 51 caracteres | recusada (`varchar(50)`); 50 acentuados aceitos |
| G-I5 | dois imóveis do mesmo dono, "Apto 101" e "APTO 101" | segundo recusado por `uq_imoveis_usuario_identificador` |
| G-I6 | "Apto 101" para dois donos diferentes | aceitos |
| G-I7 | `DELETE FROM usuarios` de quem tem imóvel | recusado por `fk_imoveis_usuario` |
| G-S1 | subida em banco vazio | `flyway_schema_history` com V1 e V2 aplicadas; `ddl-auto=validate` passa |
