# Padrão de persistência

Guia para quem for persistir um agregado novo (`Inquilino`, `Contrato`, `Fatura`, `Usuario`).
O exemplo concreto é a tabela `imoveis`, a primeira a seguir o padrão (feature
`specs/001-better-db-schema/`). Em caso de dúvida, o código citado aqui é a referência.

Arquivos de referência:

- Migração: `src/main/resources/db/migration/V1__cria_tabela_imoveis.sql`
- Mapeamento JPA: `src/main/java/br/com/marden/habitattio/adapters/outbound/persistence/entity/ImovelJpaEntity.java`
- Domínio: `src/main/java/br/com/marden/habitattio/domain/model/Imovel.java`
- Configuração: `src/main/resources/application.properties` (modo rápido) e
  `src/main/resources/application-prod.properties` (profile `prod`)
- Testes: `ImoveisPostgresConstraintsTest`, `ImovelJpaEntityMapeamentoH2Test` (em
  `src/test/java/br/com/marden/habitattio/adapters/outbound/persistence/`) e
  `EstruturaBancoProducaoTest`
- Garantias formais de `imoveis`: `specs/001-better-db-schema/contracts/imoveis-schema.md`

A estrutura de `imoveis` hoje:

```sql
CREATE TABLE imoveis (
    id             bigint GENERATED BY DEFAULT AS IDENTITY,
    endereco       varchar(255)  NOT NULL,
    valor_sugerido numeric(19,4) NOT NULL,
    ativo          boolean       NOT NULL,
    CONSTRAINT pk_imoveis PRIMARY KEY (id),
    CONSTRAINT ck_imoveis_endereco_nao_vazio CHECK (endereco !~ '^\s*$'),
    CONSTRAINT ck_imoveis_valor_sugerido_positivo CHECK (valor_sugerido > 0)
);
```

---

## (a) Nomes

- **Tabela**: em português, no plural, em snake_case. `Imovel` → `imoveis`. A entity declara
  o nome explicitamente: `@Table(name = "imoveis")`.
- **Colunas**: snake_case derivado do campo Java pela estratégia de nomes padrão do Spring
  (`valorSugerido` → `valor_sugerido`). **Não** use `@Column(name = ...)`: o nome sai do
  campo, e a migração escreve o nome derivado.
- **Constraints**: sempre nomeadas, para que o erro do banco diga qual regra foi violada.

  | Tipo | Formato | Exemplo |
  |---|---|---|
  | chave primária | `pk_<tabela>` | `pk_imoveis` |
  | chave estrangeira | `fk_<tabela>_<ref>` | (ainda sem exemplo; ex.: `fk_contratos_imoveis`) |
  | unicidade | `uq_<tabela>_<colunas>` | (ainda sem exemplo) |
  | check | `ck_<tabela>_<coluna>_<regra>` | `ck_imoveis_endereco_nao_vazio`, `ck_imoveis_valor_sugerido_positivo` |

- **Migrações**: `V<n>__<descricao_em_portugues>.sql` (ver item e).

## (b) Dinheiro

- Java: `BigDecimal` (nunca `double`/`float`). Banco: `numeric(19,4)`. Mapeamento:
  `@Column(nullable = false, precision = 19, scale = 4)`.
- Sem `precision`/`scale` o Hibernate assume `numeric(38,2)`. Declare sempre.
- 4 casas dão folga para juros e rateio; exibir em centavos é problema de apresentação, não
  de armazenamento.
- Comportamento do PostgreSQL que você precisa conhecer:
  - **Mais de 4 casas**: o banco arredonda para 4, "metade para longe do zero".
    `1500.12345` é gravado como `1500.1235`.
  - **Mais de 15 dígitos inteiros** (19 − 4): a gravação é **rejeitada**
    (`numeric_value_out_of_range`, 22003), nunca truncada.
  - O `CHECK (valor > 0)` é avaliado **depois** do arredondamento: `0.00001` vira `0.0000` e
    é rejeitado por `ck_imoveis_valor_sugerido_positivo`.
- **O domínio não arredonda.** Um `Imovel` criado com `1500.12345` mantém `1500.12345` em
  memória, enquanto o banco guarda `1500.1235`. Essa divergência abaixo da 4ª casa é
  **aceita** (spec, Clarifications). Se um agregado precisar rejeitar valores com mais de 4
  casas, isso é regra nova de domínio e volta para a spec.

## (c) Chave primária

- Banco: `id bigint GENERATED BY DEFAULT AS IDENTITY` + `CONSTRAINT pk_<tabela> PRIMARY KEY (id)`.
- JPA: `@Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id;`
- **Por que `BY DEFAULT` e não `ALWAYS`**: o adapter repassa `imovel.getId()` para a entity
  (o construtor de `ImovelJpaEntity` recebe o `id`). Com `ALWAYS`, um id explícito seria
  recusado pelo banco. `BY DEFAULT` gera o id quando ele não vem e aceita quando vem.

## (d) Onde mora cada regra

| Tipo de regra | Domínio (construtor) | Banco |
|---|---|---|
| Invariante simples sobre um membro da própria entidade (não nulo, não em branco, tamanho, `> 0`) | sim, primeiro | **também**, como `NOT NULL` / `CHECK` / tamanho do tipo |
| Regra que depende de outros objetos ou de estado externo (ex.: imóvel inativo não recebe contrato; contrato encerrado não gera fatura) | sim (ou no caso de uso) | não |

Em `imoveis`: cada `if` de `Imovel.validar(...)` tem um par no banco.

| `Imovel.validar` | Banco |
|---|---|
| `endereco == null \|\| endereco.isBlank()` | `NOT NULL` + `ck_imoveis_endereco_nao_vazio` |
| `endereco.codePointCount(...) > 255` | `varchar(255)` |
| `valorSugerido == null \|\| valorSugerido.compareTo(BigDecimal.ZERO) <= 0` | `NOT NULL` + `ck_imoveis_valor_sugerido_positivo` |

Regras do padrão:

- **O domínio valida primeiro**, com `IllegalArgumentException` e mensagem em português. O
  banco é a segunda barreira, para quem contornar o domínio.
- **O domínio pode ser mais estrito que o banco.** Exemplo: `isBlank()` trata espaços
  Unicode (` `) como branco; a regex `\s` do PostgreSQL (`!~ '^\s*$'`) cobre só os
  espaços ASCII (espaço, tab, `\n`, `\r`, `\f`, `\v`). Divergência aceita: o banco garante
  pelo menos os ASCII. Não use `btrim(col) <> ''`: ele só remove espaços, e um texto só com
  tab passaria.
- **Se o banco limita o tamanho de um texto, o domínio também limita, contando code points**
  (`s.codePointCount(0, s.length())`), não `length()`. O `varchar(n)` do PostgreSQL conta
  caracteres: `"ã"×254 + "🏠"` tem 255 caracteres e é aceito, mas `length()` daria 256.
- **Sem `DEFAULT`** em colunas cujo valor vem da aplicação (ex.: `ativo`): um `DEFAULT`
  esconderia o esquecimento.
- **Sem `UNIQUE`** que a regra de negócio não peça (dois imóveis podem ter o mesmo endereço).
  Quando a regra pedir (ex.: uma fatura por contrato e `mes_referencia`), ela vira
  `uq_<tabela>_<colunas>`.

## (e) Evolução da estrutura

- Toda mudança de estrutura do banco de produção é uma **migração Flyway nova**:
  `src/main/resources/db/migration/V<n>__<descricao_em_portugues>.sql`, SQL puro do
  PostgreSQL. Ex.: `V2__cria_tabela_inquilinos.sql`.
- **Nunca edite uma migração já aplicada.** O Flyway guarda o checksum de cada uma em
  `flyway_schema_history` e recusa a subida se o arquivo mudar. Corrigir = migração nova.
- **Mapeamento JPA e migração mudam no mesmo commit.**
- No profile `prod`, o Flyway migra e depois o Hibernate confere com
  `spring.jpa.hibernate.ddl-auto=validate` (estado-alvo da feature; ver nota abaixo). O
  `validate` acusa tabela ausente, coluna ausente e tipo incompatível, e a aplicação não sobe.
  Ele **não** confere `CHECK`, tamanho de `varchar` nem precisão/escala de `numeric`. Por
  isso os testes de constraints e de mapeamento do item (f) são **obrigatórios**: são eles,
  não o `validate`, que pegam um `CHECK` esquecido ou um `scale` errado.
- **O H2 do modo rápido não segue as migrações**: lá a estrutura sai do mapeamento JPA
  (`ddl-auto=update`, Flyway desligado). Ele não tem os `CHECK`s e pode aceitar dado que o
  PostgreSQL rejeita. A prova das regras roda sempre contra o PostgreSQL.

> Nota: durante a feature 001, o `application-prod.properties` nasceu com `ddl-auto=none` e
> passa a `validate` na US2 (task T015). Este documento descreve o estado final.

## (f) Testes

Para cada tabela nova, três tipos de teste.

### 1. Constraints no PostgreSQL — molde `ImoveisPostgresConstraintsTest`

```java
@DataJpaTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)
@ActiveProfiles("prod")
@Import(TestcontainersConfiguration.class)
class ImoveisPostgresConstraintsTest { ... }
```

- `replace = NONE` + `prod` + `TestcontainersConfiguration`: roda contra o PostgreSQL do
  container, com a estrutura criada pelas **migrações**, não pelo Hibernate.
- **Grave com SQL direto** (`JdbcClient`), contornando domínio e JPA. A pergunta do teste é
  "o banco barra?", não "o domínio barra?".
- **Ao menos um teste por garantia** do contrato da tabela (em `imoveis`: G1–G11 e G4b de
  `contracts/imoveis-schema.md`), incluindo os casos aceitos (limite exato, valores
  repetidos permitidos, arredondamento).
- **Assert pela exceção e pelo nome da constraint**: `DataIntegrityViolationException` e
  mensagem contendo `ck_...`. Para violações sem nome (`NOT NULL`, tamanho do `varchar`,
  overflow do `numeric`) basta a exceção.
- **Leia de volta por SQL**, nunca pelo adapter: não dependa de estado reidratado (o
  `ativo` de `imoveis` já teve defeito de reidratação).
- Cada teste roda em transação com rollback; os testes não interferem entre si.
- Comentário com o ID da garantia acima de cada teste (`// G6`).

### 2. Mapeamento no H2 — molde `ImovelJpaEntityMapeamentoH2Test`

- `@DataJpaTest` no modo padrão (H2, estrutura gerada pelo mapeamento).
- Consulta `INFORMATION_SCHEMA.COLUMNS` e confere `NUMERIC_PRECISION`/`NUMERIC_SCALE`
  (19/4) e `CHARACTER_MAXIMUM_LENGTH` (255).
- Motivo: no PostgreSQL a estrutura vem da migração e o `validate` não confere precisão nem
  tamanho, então `precision`/`scale`/`length` da entity só têm efeito observável no H2.
  Sem esse teste, o mapeamento pode divergir da migração em silêncio.

### 3. Subida em produção — `EstruturaBancoProducaoTest`

Sobe a aplicação real com o profile `prod` contra um `PostgreSQLContainer` próprio por
cenário (o cenário altera a estrutura), sem servidor web. Cenários do contrato:

| # | Estado do banco | Resultado esperado |
|---|---|---|
| S1 | vazio | aplica as migrações e sobe; tabela e `ck_*` existem |
| S2 | migrações já aplicadas | não reaplica nada e sobe |
| S3 | tabela sem uma coluna mapeada, ou com tipo incompatível | não sobe; o erro cita a coluna; o banco não é alterado |
| S4 | checksum de migração aplicada adulterado em `flyway_schema_history` | não sobe |

Ao criar uma tabela nova, estenda S1 para conferir que ela e suas constraints existem.

## Modos de execução

| | Modo rápido (padrão) | Profile `prod` |
|---|---|---|
| Ativação | nenhum profile | `SPRING_PROFILES_ACTIVE=prod` |
| Banco | H2 em memória (modo PostgreSQL) | PostgreSQL |
| Estrutura | Hibernate, `ddl-auto=update` | Flyway (migrações) + `ddl-auto=validate` |
| Flyway | desligado (`spring.flyway.enabled=false`) | ligado |
| Constraints `CHECK` | não existem | existem |

- **Conexão do `prod`**: URL, usuário e senha **não ficam em arquivo**. Vêm de
  `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME` e `SPRING_DATASOURCE_PASSWORD`.
  Sem elas a subida falha cedo.

  ```bash
  SPRING_PROFILES_ACTIVE=prod \
  SPRING_DATASOURCE_URL=jdbc:postgresql://localhost:5432/habitattio \
  SPRING_DATASOURCE_USERNAME=... SPRING_DATASOURCE_PASSWORD=... \
  ./mvnw spring-boot:run
  ```

- **Com containers** (sem PostgreSQL próprio): `TestHabitattioApplication`
  (`./mvnw spring-boot:test-run`), que usa `TestcontainersConfiguration`. Nos testes, o
  `@ServiceConnection` fornece a conexão e dispensa as variáveis de ambiente.
- **Versões fixas** dos containers, como constantes em `TestcontainersConfiguration`:
  `POSTGRES_IMAGE = "postgres:18.6"` e `REDIS_IMAGE = "redis:8.10.3"`. Nunca `latest` nem
  tag só de major. Testes novos reutilizam essas constantes.
- Os testes de PostgreSQL exigem Docker. Sem Docker, eles não rodam, e o relatório diz isso.

## Fora deste padrão (ainda)

- **Criptografia do CPF**: quando `Inquilino` for persistido, o CPF deve ser guardado
  criptografado. Isso não é coberto aqui e será decidido na feature de `Inquilino`. O padrão
  não impede: a coluna continua seguindo os itens (a)–(f), e a forma de cifrar entra no
  adapter/mapeamento dessa feature.
- **Tratamento HTTP de `IllegalArgumentException`** do domínio (hoje chega ao cliente sem
  handler) e o **defeito de reidratação** de `ativo` em `Imovel` foram observados, mas estão
  fora do escopo desta feature.

## Checklist: ao persistir um novo agregado

- [ ] Spec e plan da feature existem (AGENTS.md §4).
- [ ] Invariantes simples do construtor listadas; cada uma tem par no banco (`NOT NULL`,
      `ck_*`, tamanho). Regras entre agregados ficam só na aplicação.
- [ ] Texto com limite no banco ⇒ o domínio também limita, por `codePointCount`.
- [ ] Testes escritos antes e vistos falhar: constraints no PostgreSQL (SQL direto, um por
      garantia, assert pelo nome da `ck_*`) e mapeamento no H2.
- [ ] Migração nova `V<n>__<descricao>.sql`: tabela no plural em snake_case,
      `bigint GENERATED BY DEFAULT AS IDENTITY`, dinheiro `numeric(19,4)`, constraints
      nomeadas, sem `DEFAULT` escondendo esquecimento.
- [ ] `*JpaEntity` com `@Table(name = ...)`, `@GeneratedValue(strategy = IDENTITY)`,
      `nullable`/`length`/`precision`/`scale` explícitos, sem `@Column(name = ...)`.
- [ ] Migração e mapeamento no mesmo commit; nenhuma migração antiga editada.
- [ ] `EstruturaBancoProducaoTest` (S1) cobre a tabela nova.
- [ ] `./mvnw test` com Docker; se os de integração não rodaram, isso está no relatório.
